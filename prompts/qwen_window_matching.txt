Match one selected robot-video window to the complete task checklist and
bind task entities to supplied, already generated YOLO candidate IDs.

INPUT AND LIMITS

You receive the original instruction, all requirements, the complete
checklist, the selected window ID/range, the expert catalog, candidate
metadata, and ALL chronological original frames in the window (including
both endpoints) with original frame IDs and presentation timestamps.
Each original image is followed by a separate annotated view of that same
frame: boxes, mask outlines, full candidate IDs, and a class/score ledger.
The original image is authoritative when annotations obscure details.
Candidate masks already exist; do not propose rerunning YOLO.

Use the instruction as authoritative. Do not select/change windows,
add/remove checks, rename or invent entity keys, answer checks, or score.
Checklist rationales are proposals, not verified completion evidence.
Consider every check, including those citing observations outside this
window. You have not seen unprovided windows.

ASSOCIATIONS

Return exactly one relevance entry for every check:
- related: this window bears on the check, even if only partially.
- unrelated: relevance is not supported here; experts must be empty.
- uncertain: visibility, identity or temporal context prevents deciding.
Explain uncertainty in limitations. Related checks without useful expert
coverage also need limitations; retain these checks with empty experts.
Choose only experts in the catalog, at most once per check. These are
proposals for the next stage; geometry and motion have NOT been executed.
No 2D box/mask overlap or local motion establishes 3D support, contact,
grasp, release, stability or episode-wide task completion by itself.

ENTITY BINDINGS

A candidate ID such as f120:d1 identifies a detection ONLY in frame 120.
It is not a cross-frame identity. Detection classes and scores do not
establish which object the instruction means; two apples remain distinct
candidates. Use the instruction and temporal visual context to choose.
Never invent candidates, boxes, masks, class support or execution results.
The fixed detector vocabulary may miss grippers, pegs and lab props.

Use one shared binding per (entity_key, frame_id) in this window, reusable
across checks. Supply exactly the bindings required by the proposals:
- object_spatial: every proposed entity in every proposed frame.
- short_window_motion: target, and reference for relative motion, ONLY
  at the proposed interval's FIRST frame; later frames are tracking input,
  not a demand to bind every frame. Do not include unused extra bindings.

Each binding must contain exactly:
- entity_key: an unchanged key declared by the complete checklist.
- frame_id: the supplied original frame ID.
- status: bound or missing.
- candidate_id: an existing ID in that exact frame for bound; null for
  missing. If no candidate fits or identity is ambiguous, use missing.
- reason: a concise visual basis for the selection or specific reason
  why binding is missing. Never guess from class name alone.

A clear box/identity may be bound even when mask_status is empty. This
does not make a usable tracking seed; retain that mask limitation. Do not
turn a missing binding into a check verdict or delete the associated
expert proposal solely because its binding is missing.

EXPERT PROPOSALS

object_spatial proposals must contain exactly:
- expert_id: object_spatial.
- entity_keys: distinct keys declared by this check, at least one.
- frame_ids: distinct supplied frames in chronological order.
- reason: why using these existing candidates/2D geometry would help,
  with its partial scope and limitations.

short_window_motion proposals must contain exactly:
- expert_id: short_window_motion.
- target_entity_key: an explicit target declared by this check.
- motion_mode: absolute or relative (image-plane motion).
- reference_entity_key: null for absolute; an explicit distinct entity
  declared by this check for relative. Do not infer roles from list order.
- frame_ids: EVERY original frame of the proposed continuous interval,
  in order, with at least two frames. The first frame supplies the seeds.
- reason: why this motion evidence would help this check, with its scope.

For relative motion, explicitly identify the reference. Target/reference
must not bind to the same candidate. If a role cannot be identified, do
not invent it: retain the related check, omit the unsupported proposal and
explain the role uncertainty in limitations. If roles are explicit but a
seed binding is missing, keep the proposal and the missing binding/reason.
Motion additionally needs reliable masks, textured points and continuous
frames; record empty masks, occlusion and possible camera motion. This
stage neither judges mask reliability as an execution guarantee nor runs
tracking or replaces missing data with zero motion.

OUTPUT

Return only one JSON object with exactly window_id, checks, bindings.
window_id must match the supplied window. Each checks entry must contain
exactly check_id, relevance, reason, experts, limitations. All check IDs
must occur exactly once. limitations is an array of strings.
Do not include check answers, grades, measurements, boxes or mask arrays.
Use concise English, no Markdown and no reasoning transcript.
The context and labelled image pairs follow.
